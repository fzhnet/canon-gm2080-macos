# The GM2080 wire protocol, and how it was determined

The GM2000/GM2080 series accepts exactly one thing on TCP port 9100: a stream
of IVEC XML command blocks with PWG Raster page data interleaved. This
documents the format the native driver implements, and — more usefully — how
each part was established, so the results can be checked rather than trusted.

## Method: use Canon's own driver as an oracle

Canon publishes a Linux driver (`cnijfilter2`) that supports this printer.
Running it in a container with the queue pointed at a `file://` device makes it
write its output to disk instead of to the printer. That gives a generator of
ground-truth `(job options) -> (exact bytes)` pairs, on demand, without paper.

Every value below was read back from that oracle. This matters: one of them
was guessed wrong first. The `businesscard` page size looks like it should map
to the PWG standard name `om_business-card_55x91mm`, and it does not — Canon
sends the private name `custom_canon_55x91mm`. Guessing would have produced a
driver that failed on exactly one paper size.

## Overall structure

Blocks are concatenated with **no framing whatsoever** — no length prefixes,
no checksums, no escaping, no alignment. Each XML block ends `</cmd>` and the
next begins `<?xml`. Raster payloads sit directly between blocks.

```
StartJob
SetJobConfiguration
SetConfiguration
    VendorCmd   (nextpage=ON)
    SendData    (datasize=N1)
    <PWG Raster stream, N1 bytes>
    VendorCmd   (nextpage=ON)
    SendData    (datasize=N2)
    <PWG Raster stream, N2 bytes>
    VendorCmd   (nextpage=OFF)      <- last page
    SendData    (datasize=N3)
    <PWG Raster stream, N3 bytes>
EndJob
```

Confirmed against a three-page job: ten blocks, `nextpage` ON/ON/OFF, and
three separate PWG streams (three `RaS2` magic numbers), each preceded by a
`SendData` whose `datasize` equals that stream's exact length.

A single-page job is the same with one `VendorCmd`/`SendData` pair and
`nextpage=OFF`.

## The commands

All blocks share the envelope:

```xml
<?xml version="1.0" encoding="utf-8" ?>
<cmd xmlns:ivec="http://www.canon.com/ns/cmd/2008/07/common/"
     xmlns:vcn="http://www.canon.com/ns/cmd/2008/07/canon/">
  <ivec:contents>
    <ivec:operation>NAME</ivec:operation>
    <ivec:param_set servicetype="print"> ... </ivec:param_set>
  </ivec:contents>
</cmd>
```

`jobID` is an eight-digit decimal string, identical in every block of a job.
Canon writes empty elements self-closed (`<ivec:jobname/>`); the native driver
mirrors that.

| Operation | Parameters |
|---|---|
| `StartJob` | `jobID`, `bidi=0`, `forcepmdetection=OFF`, `jobname`, `username`, `computername`, `job_description` (CDATA, a UUID), `host_environment` |
| `SetJobConfiguration` | `jobID`, `mismatch_mode=none`, `datetime` (`YYYYMMDDhhmmss`, local time) |
| `SetConfiguration` | `jobID`, `papersize`, `papertype`, `borderlessprint`, `printcolormode`, `duplexprint` |
| `VendorCmd` | `jobID`, `vcn:ijoperation=SetPageConfiguration`, `vcn:nextpage` |
| `SendData` | `jobID`, `format=PWGRaster`, `datasize` |
| `EndJob` | `jobID` |

## Media tables

`papersize` values are mostly PWG self-describing names, with one exception.

| PPD `PageSize` | `papersize` |
|---|---|
| `A4` | `iso_a4_210x297mm` |
| `Letter` | `na_letter_8.5x11in` |
| `legal` | `na_legal_8.5x14in` |
| `A5` | `iso_a5_148x210mm` |
| `B5` | `jis_b5_182x257mm` |
| `Postcard` | `jpn_hagaki_100x148mm` |
| `envelop10p` | `na_number-10_4.125x9.5in` |
| `envelopdlp` | `iso_dl_110x220mm` |
| `businesscard` | `custom_canon_55x91mm` — **not** the PWG name |

`papertype` is a standard keyword only for plain paper; the rest are Canon
ordinals.

| PPD `MediaType` | `papertype` |
|---|---|
| `plain` | `stationery` |
| `highres` | `custom-media-type-canon-9` |
| `ijpostcard` | `custom-media-type-canon-11` |
| `postcard` | `custom-media-type-canon-12` |
| `envelope` | `custom-media-type-canon-18` |

## The raster payload

Standard PWG Raster (`RaS2`), one complete stream per page. For A4 at 600 dpi
Canon emits:

| | |
|---|---|
| dimensions | 4800 × 6826 |
| bits per colour | 8 |
| bits per pixel | 24 |
| bytes per line | 14400 |
| colour order | 0 (chunked) |
| colour space | 19 (sRGB) |

Two things about this are easy to get wrong:

**It is continuous-tone sRGB, not 1-bit black.** The GM2080 is a single-black
machine, so declaring `*ColorDevice: False` in the PPD is the intuitive move —
and it produces a 1-bit halftoned raster the firmware is not expecting. Canon
sends 24-bit sRGB and lets the printer do its own halftoning.

**It covers the imageable area, not the sheet.** 4800 × 6826 at 600 dpi is
576 × 819.12 pt, which is exactly the A4 imageable area from Canon's PPD
(`9.64 14.38 585.64 833.50`), not the 595 × 842 pt sheet.

This second point rules out the obvious implementation. Piping CUPS raster
through the system's `rastertopwg` yields a *full-page* raster — that filter
pads the margins back in, because full-page rasters are the PWG convention.
Every page would be offset by the margin width. The native driver therefore
converts in-process with libcups' `CUPS_RASTER_WRITE_PWG` mode, which
preserves the incoming geometry; the CUPS raster arriving from the PPD is
already exactly right.

## Verifying a change

Regenerate a reference stream from the oracle and compare structurally —
field-by-field on the XML, and header fields on each PWG page. The two
differences that are expected and correct are `datasize` (the macOS and Linux
rasterisers compress differently) and the volatile per-job values `jobID`,
`datetime` and `job_description`.
